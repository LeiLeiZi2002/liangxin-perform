# 量规到代码的映射方案

把《热线心理支持职业胜任力测评量规》落成可实现的评分链路。本文是设计文档，供施工参照。

## 设计前提

1. **量规是唯一依据。** `app/reports/evaluator.py` 是旧稿，不作为设计约束。
2. **只覆盖心理热线场域。** 量规第一节限定为实时语音热线。
3. **不做总分，不做合格判定。** 量规第九节与计划书 2.2.5。
4. **AI 不独立裁定。** 计划书 2.2.3：AI 承担证据整理与辅助评分，最终依据人工复核。
5. **模型失败不得转嫁给受测者。** 系统分析失败与受测者材料不足是两件事，分别记录。

### 系统当前定位

对外一律采用以下表述，不加强也不弱化：

> 本系统已建立从原始材料、意义单元、行为编码、量规映射到报告结论的可追溯证据链，并对隐藏信息、材料不足、模型失败、规则封顶和人工修订作了明确隔离。当前结果用于发展性反馈。系统后续将通过模型评分运行稳定性、专家一致性、内容效度和反应过程研究，逐步建立评分可信度证据。

**过程严谨不等于结论可信**：本方案保证的是每个结论可追溯、系统不声称它没资格声称的东西、出错时错误可被定位；不保证等级准确，也不保证评分稳定。后者需要第十节及其后续研究提供证据。

效度现状的准确表述是：**当前只有标准、文献和案例设计提供的初步内容依据，尚未形成经过专家审定和实测支持的完整效度证据。**

## 一、评分链路总览

```
对话记录 + 工作记录
        ↓
① 两个连续材料分片并行做局部质性编码（两次模型调用）
   意义单元、开放编码、精确材料引用
        ↓
② 聚焦汇总（一次模型调用）
   去重整合、指标映射、反例检索、材料冲突与底线候选
        ↓
③ 程序校验：引用核验、证据路由分流、机会兑现核对
        ↓
④ 生成各维度 DimensionPacket
        ↓
⑤ 三组并行提出等级建议（三次模型调用）
        ↓
⑥ 规则收口：未评分判定、等级封顶、底线事件、报告组装
```

### 为什么分成「两路局部编码 + 一次聚焦汇总 + 三组定级」

- **局部编码需要控制任务负荷。** 两个连续分片分别完成意义单元划分和开放编码，模型不必在一次长输出里同时完成分段、指标映射、反例检查和底线判断。两个分片并行调用，不增加串行等待。
- **反例检查仍需要跨片段语境。** 聚焦汇总读取两份已经过引用核验的局部编码，统一完成指标映射、反例检索、后续修复核对、材料冲突和底线候选判断，避免按维度切开后看不到前后变化。
- **等级建议不需要全局语境。** 定级只需要已核验的证据包和对应锚点。分组后单次输出结构可控，某组失败只重试该组。

正常成功路径共六次模型调用：两次 Map（局部编码）、一次 Reduce（聚焦汇总）、三次 Group（分组定级）。结构校验失败后的针对性修复会额外调用，并以修复调用单独留痕。

### 三组划分

| 组 | 范围 |
|---|---|
| 互动过程组 | C1、C2、C3、C5、C6、C8，及 S3、S5、S6 |
| 专业判断组 | C4、C7、C9，及 S4、S7、S8 |
| 安全组 | S1a、S1b、S2 |

后三组只读 `DimensionPacket` 与对应量规锚点，不重复读取整通记录。稳定的量规文本可复用上下文缓存。

## 二、输入契约

### 2.1 进入编码模型的材料

| 材料 | 来源 |
|---|---|
| 对话记录 | `TurnRecord`，含 `turn_id`、说话人、时间、原文 |
| 工作记录 | `WorkRecordRecord` 全部字段 |
| 技术事件 | 重连、ASR 失败、来电者主动挂断的时间点 |

### 2.2 禁止进入编码模型的材料

| 材料 | 理由 |
|---|---|
| `ActorState`（紧张度、情绪强度、继续意愿） | 量规第二节：内部状态只用于确认机会是否出现，不作能力证据 |
| 案例事实编号与未披露事实 | 量规 C4：未披露事实不能用来判定漏评 |
| 案例中对受测者不可见的关系人真实状态（`relationships[].actual_state`） | 与内部状态同理：只用于判定机会是否兑现，不作能力证据 |
| 评分机会声明 | 会诱导模型照着答案找证据 |

**结构上隔离**：`CodingInput` 与 `OpportunityCheckInput` 是两个类型，前者拿不到 `ActorState` 和案例事实。编码模型只看受测者真正听见、说出和写下的材料。

### 2.3 评分材料冻结

**报告任务创建时冻结全部评分输入，此后不再重新读取。** 冻结内容：

- 按顺序排列的最终对话转写；
- 已提交的工作记录全文；
- 技术中断事件；
- 量规常量、案例包、模型与提示词的内容指纹；
- 整份评分输入的内容指纹。

理由：链路是异步的，第一轮编码与三组定级之间相隔数十秒到数分钟。若期间材料可变，同一份报告的不同阶段会读到不同内容，证据引用校验会随机失败，运行稳定性数据也不可比。

现状缺口：`put_work_record` 只在 `ReportRecord` 已存在时拒绝修改。异步化后，任务运行期间报告记录尚未生成，工作记录仍可被改——而 C4、C7、C9 以工作记录为主要证据。

### 2.4 材料种类

```python
class MaterialKind(StrEnum):
    dialogue = "dialogue"          # 对话记录
    audio = "audio"                # 音频派生事件
    work_record = "work_record"    # 工作记录
    opportunity = "opportunity"    # 案例机会与披露记录
```

`opportunity` 只出现在机会兑现核对，不进证据集。

### 2.5 证据引用结构

必须支持三类来源，互斥联合而非统一 `turn_id`——C4、C7、C9 以工作记录为主要证据，用话轮编号无法表示。

```python
class DialogueRef(BaseModel):
    kind: Literal["dialogue"]
    turn_id: str
    quote: str            # 必须是该话轮原文的连续子串

class WorkRecordRef(BaseModel):
    kind: Literal["work_record"]
    field: str            # 工作记录字段名
    quote: str            # 必须是该字段原文的连续子串

class AudioEventRef(BaseModel):
    kind: Literal["audio_event"]
    event_id: str         # 指向已采集的音频派生事件

EvidenceRef = DialogueRef | WorkRecordRef | AudioEventRef
```

### 2.6 证据路由与使用权限

量规第二节的证据来源表编码为白名单，并明确每种角色的**使用权限**：

| 角色 | 权限 |
|---|---|
| `primary` | 可直接支持等级判断 |
| `supporting` | 只能补充，**不能单独把等级抬高** |
| `cross_check` | 只用于核对冲突与一致性，**不作正向加分证据** |
| `opportunity_only` | 只用于确认机会是否出现，不进入能力证据 |
| `excluded` | 直接拒收 |

核心维度：

| 维度 | 对话 | 音频 | 工作记录 |
|---|---|---|---|
| C1 | primary | supporting | excluded |
| C2 | primary | supporting | cross_check |
| C3 | primary | excluded | cross_check |
| C4 | primary | supporting | primary |
| C5 | primary | supporting | cross_check |
| C6 | primary | primary | excluded |
| C7 | primary | excluded | primary |
| C8 | primary | supporting | cross_check |
| C9 | cross_check | cross_check | primary |

专项模块同样入表，不留给提示词临时判断：

| 模块 | 对话 | 音频 | 工作记录 |
|---|---|---|---|
| S1a | primary | supporting | cross_check |
| S1b | primary | supporting | primary |
| S2 | primary | supporting | primary |
| S3 | primary | primary | excluded |
| S4 | primary | supporting | cross_check |
| S5 | primary | supporting | cross_check |
| S6 | primary | supporting | cross_check |
| S7 | primary | excluded | primary |
| S8 | primary | supporting | primary |

## 三、模型输出契约

### 3.1 前两轮并行：局部开放编码

程序把冻结对话切成两个连续分片，后一片向前保留少量重叠话轮，工作记录只进入后一片。局部编码不读取量规锚点，也不决定能力等级。

```python
class LocalCodedUnit(BaseModel):
    id: str
    summary: str
    initial_codes: list[str]
    refs: list[EvidenceRef]
    alternative_reading: str | None

class LocalCodingOutput(BaseModel):
    shard_id: str
    units: list[LocalCodedUnit]
```

每个局部单元必须引用该分片内的真实对话或工作记录原文。程序在进入汇总前核验编号和连续原文，引用失真只重试对应分片。

### 3.2 第三轮：聚焦汇总

聚焦汇总只读取两份通过引用核验的局部产物、固定完整的九个核心维度与九个专项模块目录及其量规指标，不读取来电者内部状态、未披露事实或案例机会声明。目标目录不得根据隐藏状态缩减；机会核对结束后，规则才从汇总产物中选择本次实际启用的专项模块。其最终产物如下：

```python
class MeaningUnit(BaseModel):
    id: str
    turn_ids: list[str]
    summary: str               # 贴近材料，不写结论

class CodedEvidence(BaseModel):
    unit_id: str
    target: CoreDimension | SpecialModule
    indicator_id: str
    direction: Literal["support", "limit", "adverse"]
    strength: Literal["strong", "moderate", "weak"]
    context: str
    alternative_reading: str | None
    ref: EvidenceRef
```

**已删除 `opportunity_present`。** 观察机会由规则在第 ② 步核对后附加到 `DimensionPacket`，模型不填也看不到机会声明。

### 3.3 反例检查（可核验的形式）

`searched: bool` 是自我声明，无法证明模型真的检查过。改为要求提交可核验的检索痕迹：

```python
class CounterCheck(BaseModel):
    target: CoreDimension | SpecialModule
    searched_unit_ids: list[str]   # 实际检索了哪些意义单元
    found: list[CodedEvidence]     # 找到的反向或修复材料
    not_found_note: str | None     # 未发现时说明检索了什么、为何判定没有
```

规则侧校验：`searched_unit_ids` 非空且都是本次实际产生的单元；`found` 为空时 `not_found_note` 必填。

### 3.4 底线事件候选（同属聚焦汇总）

底线事件中需要语义判断的四类，**必须在聚焦汇总时产出，不能留给局部编码或分组定级**。理由与反例检查相同：一段羞辱性发言可能只被编码到 C1，但判定它是否构成底线，需要结合另一分片里的后续修复和是否反复出现。分组后各组只看得到自己的证据包，判不了。

```python
class BottomLineCandidate(BaseModel):
    category: Literal[
        "humiliation_or_coercion",      # 羞辱、歧视、威胁、强迫
        "false_confidentiality",        # 虚假承诺绝对保密
        "encouraged_harm",              # 鼓励自伤、他伤或违法
        "private_relationship",         # 建立私人、排他或利用性关系
    ]
    refs: list[EvidenceRef]
    context: str
    repair_observed: bool               # 整通材料中是否出现后续修复
    reasoning: str
```

规则可判的两类（明知危险却结束、工作记录编造）由规则侧在第 5.6 节产出，不进本契约。

### 3.5 后三轮并行：等级建议

输入是 `DimensionPacket`，不含整通原文：

```python
class DimensionPacket(BaseModel):
    target: CoreDimension | SpecialModule
    rubric: CoreRubric | ModuleRubric        # 指标、锚点、排除范围
    evidence: list[CodedEvidence]            # 已通过引用校验与路由分流
    counter_evidence: list[CodedEvidence]
    units: list[MeaningUnit]                 # 仅上述证据涉及的单元
    opportunities: list[OpportunityOutcome]  # 本维度的机会兑现结果
    conditional_unavailable: list[str]       # 无机会的条件行为
```

`opportunities` 只带兑现结论，不带案例事实原文与机会描述，避免模型照着答案倒推。

```python
class LevelProposal(BaseModel):
    target: CoreDimension | SpecialModule
    proposed_level: int | None
    pattern: str
    rationale: str
    representative_units: list[str]
    limiting_units: list[str]
    next_level_gap: list[str]        # 与下一等级相比仍缺少的可观察行为
    evidence_confidence: Literal["high", "medium", "low"]
    evidence_confidence_factors: list[str]   # 结构化因子，由规则生成表述
```

模型输出的全部自然语言字段使用中文，与量规和报告一致。

`next_level_gap` 与 `confidence_source` 对应量规第七节第 7 步「报告证据链」的第 5、6 项，是报告的必需内容，必须由模型在此产出，不能在组装阶段编造。

## 四、模型失败与材料不足的分离

这是本方案的一条硬规则：**「材料不足」评价的是受测者留下的材料，模型漏字段属于系统分析失败，两者不得混淆。**

```python
class UnscoredReason(StrEnum):        # 受测者侧，进报告
    no_opportunity = "no_opportunity"
    insufficient_evidence = "insufficient_evidence"
    technical_failure = "technical_failure"

class AnalysisOutcome(StrEnum):       # 系统侧，内部记录
    ok = "ok"
    analysis_failed = "analysis_failed"
```

处理顺序：

1. 输出不完整或校验不通过 → 仅重试相应批次，**最多重试两次**。
2. 重试仍失败 → 该维度记 `analysis_failed`，**不生成结论**。
3. 报告中如实显示「本维度分析未完成」，不写成受测者材料不足，也不计入证据覆盖。

`analysis_failed` 不进 `UnscoredReason`，两者在报告里分开呈现。

## 五、规则侧校验与裁定

### 5.1 引用校验

- `DialogueRef.turn_id` 存在于原始话轮，`quote` 是其原文连续子串。
- `WorkRecordRef.field` 是工作记录的合法字段，`quote` 是该字段原文连续子串。
- `AudioEventRef.event_id` 存在于已采集事件。
- `ref.kind` 对应的来源在该维度路由中不为 `excluded`。
- `indicator_id` 属于该维度。

不通过的证据丢弃并记录。若某维度全部证据被丢弃：区分是模型引用错误（→ `analysis_failed`）还是本就没有可用材料（→ `insufficient_evidence`）。

### 5.2 机会兑现核对

```python
class OpportunityOutcome(BaseModel):
    opportunity_id: str
    declared_target: CoreDimension | SpecialModule
    kind: Literal["required", "conditional"]
    fulfilled: bool
```

这一步**允许读 `ActorState` 与案例事实**（2.2 的唯一例外），因为它判定的是情景有没有出现，不是能力。

- 未兑现的机会：受测者不失分，计入报告「未观察部分」。
- 专项模块启用只看案例是否声明该模块的机会，不看对话内容。S1a 默认启用。

### 5.3 未评分判定

判定顺序：`analysis_failed` → 技术中断 → 无观察机会 → 材料不足。

### 5.4 证据充分性

默认两个相互独立的互动片段。规则可判定的部分：`representative_units` 中的两个单元 `turn_ids` 无交集，且不是同一单元重复计入。

四条豁免：触发底线事件的关键事件、案例只声明了该维度一个机会、来电者挂断或技术中断使该片段成为唯一有效机会、C8 固定豁免。

### 5.5 等级封顶

规则强制，不指望模型自觉：

| 条件 | 封顶 |
|---|---|
| 存在 `direction == "adverse"` 的有效证据 | 不高于 2 级 |
| 该维度条件行为无兑现机会 | 不高于 3 级 |
| 缺复杂观察机会 | 不高于 3 级 |

结果记录 `caps_applied`，让复核者看出等级是模型判的还是规则压的。

### 5.6 底线事件

六类的判定能力不同，分三档处理：

**规则可判（需三项证据同时成立）**

- *明知紧迫危险却结束通话且无安全安排*：① 风险信息已在某一话轮**向受测者披露**；② 披露后受测者确实获得处理机会（有后续话轮）；③ 通话结束前无相应安全行动。
  **不得**依据来电者隐藏的真实风险状态判定「明知」。

**规则生成候选冲突 + 语义判断**

- *工作记录编造关键事实或已执行行动*：工作记录是自由文本，系统无对应事件不等于编造。规则只产出「记录与通话不对应」的候选冲突，由语义分析判断是编造、笔误还是合理概括。除非将来把「已联系督导」这类写成与系统事件绑定的结构化字段，否则不升级为规则直判。

**语义判断**

- 羞辱歧视威胁强迫、虚假承诺绝对保密、鼓励危险行为、建立私人排他关系。

```python
class BottomLineEvent(BaseModel):
    id: str
    category: str                    # 六类之一
    detection: Literal["rule", "semantic", "rule_candidate_semantic_confirmed"]
    refs: list[EvidenceRef]
    description: str
    reasoning: str
```

底线事件独立于维度等级单独入库，不受任何维度等级影响，也不因其他维度高等级而减弱。

### 5.7 材料冲突

量规第九节：材料冲突时应具体列出冲突的原话、记录字段和判断影响，不写成一句概括。

```python
class MaterialConflict(BaseModel):
    id: str
    dialogue_ref: DialogueRef | None
    work_record_ref: WorkRecordRef | None
    description: str                 # 冲突是什么
    affected_targets: list[CoreDimension | SpecialModule]
    impact: str                      # 对判断的影响
```

主要来源是 C9 的记录与通话核对，以及 5.6 中「记录与通话不对应」的候选冲突。冲突本身不直接扣分，由相应维度在定级时考虑。

### 5.8 S1a 筛查缺口

S1a 判 0 或 1 级时生成 `screening_gap`「本次通话未完成基础风险筛查」。按量规第九节不计入底线事件，两者分别记录。

## 六、数据结构

### 6.1 枚举

```python
class CoreDimension(StrEnum):
    respectful_communication = "C1"
    listening_and_emotion = "C2"
    concern_clarification = "C3"
    integration_and_judgment = "C4"
    supportive_intervention = "C5"
    voice_and_process = "C6"
    boundary_and_ethics = "C7"
    closure_and_followup = "C8"
    documentation = "C9"

class SpecialModule(StrEnum):
    basic_risk_screening = "S1a"
```

## 七、报告输出

量规第九节与第七节第 7 步规定了报告内容。本节把它落成结构与生成责任。

### 7.1 结果摘要

```python
class ResultSummary(BaseModel):
    scored_core_count: int
    unscored: list[tuple[CoreDimension, UnscoredReason]]
    analysis_failed: list[CoreDimension | SpecialModule]   # 与 unscored 分开
    activated_modules: list[SpecialModule]
    inactive_modules: list[tuple[SpecialModule, str]]
    bottom_line_events: list[BottomLineEvent]
    screening_gap: bool
    level_distribution: str
    next_behaviors: list[str]
```

生成责任：

- `level_distribution` **由规则按模板生成**，不由模型撰写。模板形如「九个核心维度中六个形成等级，其中四个为 3 级、两个为 2 级，三个因无观察机会未评分」。交给模型会出现「整体表现良好」这类分类式表述，违反量规第九节。
- `next_behaviors` 汇总各维度的 `next_level_gap`，规则去重后取前若干条。
- **`analysis_failed` 与 `unscored` 必须分列**，不得合并显示。系统分析失败不是受测者的材料问题（第四节）。

摘要不得出现「合格」「通过」「达标」「优秀」等分类词。规则侧应有一个禁用词检查，命中即拒绝出报告。

### 7.2 每维度展示

按量规第七节第 7 步，每个维度至少呈现六项：

| 项 | 来源 |
|---|---|
| 等级 + **完整等级描述** | `level` + 该等级的锚点原文 |
| 主要表现模式 | `pattern` |
| 两组左右代表性证据 | `representative_unit_ids` 指向的 `evidence` |
| 限制性证据或反例 | `limiting_unit_ids` 指向的 `counter_evidence` |
| 本次提供了哪些观察机会，哪些没有 | `conditional_unavailable` + 机会兑现结果 |
| 结论置信程度及其来源 | `evidence_confidence` + 由因子生成的表述 |

**等级必须连同锚点原文一起显示，不能只显示数字。** 量规的等级是行为描述，脱离描述的「3 / 4」会被读成分数。

未评分维度显示 `unscored_reason` 的中文说明；`analysis_failed` 的维度显示「本维度分析未完成」，不显示等级位。

`caps_applied` 非空时显示封顶原因，让复核者看出等级是模型判的还是规则压的。

### 7.3 固定声明

以下文本**硬编码为常量**，不入库、不经模型、不可改写：

1. 量规第九节「本结果不支持的判断」四条（不得用于胜任判定、不得用于有后果的人事决定、不得跨案例比较、不得推断真实工作表现）。
2. 量规第九节要求醒目标注的模型生成声明。
3. 结果用途说明：发展性反馈。

### 7.4 不输出的内容

- 总分、常模、排名。
- 一致性百分比（量规第九节明确删除）。
- 自动生成的「建议人工复核」（同上，所有结果都需人工核对，单独标注无信息量）。
- 任何跨维度合成指标。

材料冲突时按量规第九节要求，具体列出冲突的原话、记录字段和判断影响，不写成一句概括。

### 7.5 与人工复核的衔接

量规规定最终以人工复核为准，同时规则侧存在硬封顶（第 5.5 节）。两者关系需明确：

- 专家**可以**覆盖规则封顶后的等级，包括向上覆盖。
- 覆盖时必须留痕：记录原等级、`caps_applied`、专家理由。
- AI 原始结果与封顶记录保留，不被覆盖抹去。

否则会出现两种坏情况：规则封顶变成不可申诉的黑箱，或专家改分后无法追溯原判依据。

### 7.6 持久化

`ReportRecord` 相应调整：

- 删除 `raw_score`、`normalized_score`。
- `coverage` 删除，由 `ResultSummary.scored_core_count` 取代，避免两个口径并存。
- `dimensions_json` 存 `DimensionResult` 列表（含核心维度与已启用模块）。
- `safety_flags_json` 改存 `BottomLineEvent` 列表。
- `consistency_json` 改存 `MaterialConflict` 列表。
- 新增 `summary_json` 存 `ResultSummary`。
- 新增 `screening_gap` 布尔字段，便于查询。

演示阶段不做数据迁移，旧报告直接丢弃。

### 7.7 前端改动

- `dimensionIdSchema` 八值替换为核心维度九值 + 专项模块九值两套。
- `labels.ts` 的 `domainNames` 相应重写，并新增未评分原因、指标状态、封顶原因的中文标签。
- 报告页首屏的总分区块替换为结果摘要。
- 维度卡片增加：完整锚点描述、封顶原因、`evidence_confidence` 及其因子表述、未观察部分。
- 专项模块与核心维度分区展示，未启用模块列出原因。

## 八、案例的能力覆盖声明

本节只规定声明机制。哪个案例实际声明了什么，属于案例编写，不由本方案锁定。

**不按维度凑机会数。** 观察机会不等于证据数量：一次自然的关系破裂与修复可能同时形成多段证据，不需要预先写成多个独立剧情机关。按维度凑机会会让案例变成刻意出题，损害计划书 2.3.2 强调的情境真实性。

声明机制：

1. **案例声明它能有效观察哪些维度与模块**，而非按维度凑数。
2. **普通交流自然覆盖**关系、理解、表达、节奏等维度，不必逐条声明剧情机关。
3. **风险、伦理、转介、第三方等由案例专项声明**，并与 `linked_fact_ids` 对应。
4. **模块启用只读案例声明**，不看对话内容（S1a 除外，默认启用）。
5. **案例集整体保证能力覆盖**，不强迫每个案例覆盖全部能力。
6. **没有声明机会的维度如实未评分**，这本就是量规的设计。

由此产生的案例编写约束（供案例作者参照，不在本方案内确定具体内容）：

- 声明某模块前，案例必须具备该模块所需的情景结构。例如 S7 要求「来电者为他人求助、要求评估未在场者或让热线直接采取行动」——把关系人写成来电者可动用的支持资源，不构成 S7。
- 需要评到 3 级以上的条件行为，案例需提供对应机会；需要评到 4 级，需提供复杂观察机会。
- 案例集层面需覆盖到拟启用的全部模块，缺口如实留白。
- **条件机会声明不等于必然启用。** 案例可以声明一条条件机会，但是否启用由实际表现是否跨过量规的启用门槛决定。例如某模块要求「持续、明显或反复」的情景，案例中一次短暂的表现可能达到门槛，也可能只是普通波动——由机会兑现核对判断，不由案例声明单方面决定。
- 启用判断可以读取人物事件状态（属第 5.2 节的例外），但**能力证据仍只能来自受测者在该片段中的实际回应**。
- 只设置一次机会的条件情景，走证据充分性豁免第二条，且该维度 `evidence_confidence` 最高为 medium，报告须说明只有一次观察机会。

## 十、模型评分运行稳定性检查

**不是信度检验。** 固定材料重复运行，测到的是评分链路的运行稳定性，主要反映模型随机性、提示词稳定性和输出契约是否稳定。它**不能**替代评分者一致性、测验信度，也不能说明量规是否稳定测量热线胜任力。对内对外一律使用「运行稳定性」，不得表述为信度证据。

### 10.1 当前阶段能做的四类早期验证

| 验证内容 | 现在能做 | 支持的结论 |
|---|---|---|
| 运行稳定性 | 固定材料重复运行 | 评分链路是否稳定 |
| 内容效度 | 请热线专家审查维度、指标、锚点与案例机会 | 量规内容是否覆盖岗位要求 |
| 专家一致性 | 两名以上专家独立评分少量固定材料 | 量规能否被不同评分者一致使用 |
| 反应过程 | 初阶工作者完成测评后访谈 | 任务是否真的引出预期的职业判断过程 |

内部结构、外部关联、经验组区分和使用后果需要一定样本，暂不可做。

本节只规定第一类的实现。后三类属于研究设计，不在本方案范围。

### 10.2 测什么

固定输入，重复运行评分链路，观察输出波动。

**输入必须固定**：已完成的对话记录 + 工作记录，不重新发起通话。隔离的是评分环节的方差；来访者每次回应不同带来的方差是另一回事，不要混。

除模型随机性外全部固定并记录：模型名称与版本、温度及采样参数、提示词内容指纹、量规常量指纹、案例包版本、缓存使用情况。**任何一项变化，此前的稳定性数据即不可比。**

### 10.3 基准材料

一份材料跑五遍只是冒烟测试，代表性太差。应准备一组覆盖判定边界的基准材料：

1. 明显达到较高锚点的表现；
2. 处于 2 级与 3 级边界的表现；
3. 含明显反向行为的表现；
4. 先失当、后完成修复的表现；
5. 工作记录与对话存在矛盾的表现；
6. 缺少观察机会或材料不足的表现。

成本紧张时的最小规模：**6 份材料 × 3 次运行**。

### 10.4 指标

| 指标 | 计算 |
|---|---|
| 等级完全一致率 | 各维度众数等级占比 |
| 相差不超过一级的比例 | 落在众数 ±1 内的占比 |
| 代表性证据单元重合度 | 各维度 `representative_unit_ids` 的 Jaccard 均值 |
| 编码方向一致性 | 支持／限制／反向三类标注的一致比例 |
| 底线事件触发一致性 | 每类底线事件出现的运行次数 |
| 未评分原因一致性 | 未评分维度及其原因是否稳定 |

其中两项比等级一致率更要紧：

- **未评分原因一致性**——同一份材料有时说能评、有时说没机会，比等级从 2 波动到 3 严重得多。
- **证据单元重合度**——重合度低而等级稳定时，等级稳定是假象，模型每次在看不同的东西。

### 10.5 方差来源分解

1. **总方差**：完整重跑（第一轮编码 + 三组定级）。
2. **定级方差**：固定一次第一轮编码输出，只重跑三组定级。

两者之差即编码环节引入的方差。总方差大而定级方差小，问题在意义单元划分与证据编码，调锚点无用；反之才是锚点区分度不够。

### 10.6 波动如何处理

**不得把重复运行的分歧直接转换成等级区间。** 三次输出 2 / 3 / 3 不是统计意义上的置信区间，只是模型运行存在分歧，把它显示成「2—3 级」等于用呈现方式掩盖实现问题。

正确的处理顺序：

1. 检查意义单元划分与证据编码是否变化；
2. 检查该维度量规边界是否含糊；
3. 调整提示词、温度与结构化契约；
4. 与专家参照结果比较；
5. 必要时该维度保留人工复核状态。

只有将来正式采用多次运行共识定级、并验证过该方法之后，才能把多次结果纳入正式报告。

### 10.7 两种「置信」必须分开

| 概念 | 含义 | 去向 |
|---|---|---|
| `evidence_confidence` | 本次证据对当前等级结论的支持程度 | 进入单次报告 |
| `system_repeatability` | 固定材料重复运行时评分链路是否稳定 | 系统验证指标，**不进受测者报告** |

两者互不蕴含：证据充分时模型实现仍可能不稳定；模型每次都输出同一等级也不代表证据充分或判断正确。

### 10.9 下一步：专家参照集

两名以上热线专家独立评价同一批基准材料，形成共识参照。届时才能比较：意义单元是否抓到相同片段、指标映射是否一致、表现方向是否一致、等级与专家判断是否一致、底线事件有无漏报误报。

**二期结束后：运行稳定性检查**

**三期：案例内容**
按第八节的机制补齐各案例的能力覆盖声明；拟启用但缺案例的模块另建案例。属内容工作，可与二期并行。
